Section 1

Executive Summary

Automated extraction with human-in-the-loop review for clinical risk adjustment.

In short. This architecture uses AI_COMPLETE to extract structured clinical fields from PDF documents, resolves bounding box coordinates using open source python libraries, and presents results in a Streamlit App for manual review. AI Function Studio optimization identified prompt and model optimization tactics to boost accuracy and reduce costs.

Healthcare organizations processing clinical documents for risk adjustment face a fundamental tension: automated extraction must be fast and scalable, but the stakes of coding accuracy demand human oversight. Errors in diagnosis capture, specificity, or supporting evidence can directly impact reimbursement accuracy and compliance. This solution streamlines the human review process necessary for compliance thresholds.

1 Semantic Extraction

A Custom AI Function wraps an AI_COMPLETE call that reads PDFs natively. The model extracts 12 structured fields per document, organized into three categories, along with review metadata for each field: whether a correctness criterion is met, a rationale, a verbatim evidence quote, a page index, and a confidence level. The full DDL and extraction prompt are documented in Appendix B.

We also evaluated AI_EXTRACT as an alternative extraction function; the head-to-head comparison is detailed in Section 6.

2 Bounding Box Resolution

ⓘ

The pipeline checks whether the PDF contains characters in its text layer. If characters are found, text-layer search resolves bounding boxes directly. Zero characters = scanned document = OCR required. This single check determines the bounding box strategy for each document.

Path A – Digital PDFs

Text-Layer Search

Documents exported from EHRs (Epic, Cerner) retain an embedded text layer. pypdfium2, an open-source Python library, searches for the evidence_quote string and returns pixel-accurate coordinates via get_charbox(). Fast (<1 second per document).

Path B – Scanned PDFs

EasyOCR Word Detection

Faxed records, photocopied charts, and handwritten notes arrive as image-only PDFs with no text layer. EasyOCR, an open-source Python library, renders each page at 150 DPI and detects word-level bounding boxes. A three-step matching algorithm locates precise field values in the OCR output. Zero AI credits.

Page-Level Optimization

OCR runs only on pages where AI_COMPLETE identified fields (using page_index). For a 50-page chart where fields appear on 3 pages, only those 3 pages are processed, shrinking the processing time.

Three-Step Matching Algorithm

After OCR, the pipeline matches field values to OCR output to ensure bounding box precision:

  1. Block-level substring match – long evidence quotes returned as single OCR detections
  2. Multi-block merge – text spanning consecutive detections across line breaks
  3. Word-by-word prefix match – fallback for shorter values

Human Review Workflow

Reviewer triage based on model self-assessment of each extraction.

1 Triage Logic

The extraction prompt codifies three per-field outputs—confidence, criterion_met, and rationale—as required elements of the LLM response. The rationale output provides the model’s reasoning for each confidence and criterion assessment, giving reviewers context without re-reading the source document.

Fields that count toward the Needs Review metric:

Prompt-Codified OutputTriage RuleReviewer Action
confidence: "low"Model flags extraction uncertaintyManual review required
criterion_met: "no"Model asserts the field is missing or illegibleVerify absence in source document
criterion_met: "insufficient_documentation"Model identifies a documentation gapFlag for provider follow-up

Medium confidence fields are informational only—shown in the confidence issues banner but excluded from the Needs Review count.

ⓘ

Prompt as configuration. Because confidence, criterion_met, and rationale are prompt-codified rather than model-native, the same pattern extends to any extraction domain. Changing the triage criteria is a prompt edit, not a code change.

Custom AI Function and Optimization

Packaging extraction as a reusable Snowflake object, evaluating quality, and optimizing for cost and accuracy.

1 Creating a Custom AI Function

The clinical extraction prompt is packaged as EXTRACT_CLINICAL_DOCUMENT using CREATE AI FUNCTION, making it a reusable, governed Snowflake object callable from any SQL query or application. The full DDL and prompt are in Appendix B.

SQL 
CREATE OR REPLACE AI FUNCTION extract_clinical_document(pdf_stage_path VARCHAR)
  RETURNS VARIANT
  AS $$
    SELECT AI_COMPLETE(
      'claude-sonnet-4-6',
      PROMPT('...extraction prompt...', TO_FILE('@PDF_STAGE', pdf_stage_path))
    )
  $$;

Section 6

AI_EXTRACT vs AI_COMPLETE

Choosing the right Cortex AI function based on extraction complexity.

1 When to Use Each Function

AI_EXTRACT is a lookup function. Given a document and a list of field labels, it returns the literal text that matches each label. It requires no prompt engineering and returns a flat JSON object. If the value is written verbatim on the page, AI_EXTRACT finds it. It supports tuning parameters like scale_factor to control OCR resolution for scanned documents at the cost of reduced page capacity.

AI_COMPLETE is a reasoning function. It follows detailed instructions, can infer unstated conditions from clinical context, assess document quality, and return rich output structures including confidence scores, rationale, and evidence quotes. It also supports tuning parameters like temperature, top_p, and max_tokens for fine-grained control over output behavior.

ⓘ

Many clinical documents do not contain explicit ICD-10 or HCC codes, but the diagnosis and supporting evidence are described in narrative text. If you need the model to interpret, infer, or assess rather than simply copy text, AI_COMPLETE is the right choice.

Section 7

Chunking Strategy for Large Documents

How many pages go into each AI function call, and why it matters.

1 What Is Chunking?

Chunking is dividing a document into page ranges that each fit within a single AI function call. For a 5-page office visit note, chunking is irrelevant – the entire document fits in one call. For a 500-page compiled patient record, chunking determines how many calls you make, what context each call sees, and how you merge results.

ⓘ

When chunking matters. Most single-encounter clinical documents (progress notes, procedure reports, radiology reports) are 1–10 pages. Chunking becomes relevant for multi-visit chart extracts, full-year patient records, and compiled audit packages that routinely exceed 100 pages.

Extraction

Structured fields from a known document

Input: One document, full context required

Goal: Pull all target fields — values can appear on any page

Chunking impact: Splitting the document risks missing fields that span or reference other pages. Send the full document when page limits allow.

Retrieval

Relevant passages from a document corpus

Input: A question across many documents

Goal: Find the most relevant passages — irrelevant content is noise

Chunking impact: Moderate chunks (~1,800 chars) with retrieval outperform stuffing full documents into context. Snowflake research found chunking strategy matters more than model choice.

3 Do You Need to Chunk?

✔ No — send the full document
  • Document is ≤ 3,000 pages and you use AI_COMPLETE with gemini-2.5-flash
  • Document is ≤ 100 pages and you use AI_COMPLETE with Claude models
  • Document is ≤ 125 pages and you use AI_EXTRACT (default)

Most single-encounter clinical documents (1–10 pages) fall here.

Tradeoff: Risk of context confusion - the model may grab the wrong date or confuse similar entities in large documents. Mitigate with better prompting, not smaller input.

⚠ Yes — chunking required
  • Document exceeds AI_EXTRACT’s 125-page hard limit (or 62 pages at scale_factor: 2.0)
  • Document exceeds 100 pages on Claude models
  • Compiled patient records, annual chart reviews, or audit packages

Patient history documents are structurally messy — encounter-based boundary detection is unreliable. Prefer fixed-size strategies below.

Tradeoff: Risk of incomplete context - cross-page references are lost, fields may duplicate across chunks, and merge logic is required to reconcile conflicting extractions.

When you do chunk, preserve document structure. Use AI_PARSE_DOCUMENT in LAYOUT mode to produce markdown that retains headers, tables, and section boundaries, then split with SPLIT_TEXT_RECURSIVE_CHARACTER at semantic boundaries (paragraphs, then sentences) rather than fixed character counts. Snowflake research on financial RAG found that markdown-aware chunking with moderate sizes (~1,800 characters) outperformed large fixed-size chunks by 5–10%, and that chunking strategy had more impact on answer quality than the choice of generative model.

4 How Chunk Size Affects Cost and Accuracy

Cost

Tokens scale with pages, not chunks

A 1,000-page document costs the same page tokens (970 tokens/page = 970k tokens) regardless of how you chunk it. The overhead comes from repeated prompts and output tokens per chunk. Fewer chunks = less overhead.

Accuracy

Larger chunks provide more cross-page context

If a diagnosis appears on page 3 and supporting lab results on page 47, a chunk spanning both can connect them. Smaller chunks lose this cross-reference. But larger chunks also introduce more noise for the model to sift through.

The hardest problem is field deduplication. Multi-visit records contain multiple encounters, each with its own patient demographics, dates, and diagnoses. Chunking at arbitrary page boundaries means each chunk may extract different values for the same field, requiring merge logic to reconcile.

Appendix B

Custom AI Function Definition

Full DDL and extraction prompt used in this workflow.

SQL 
CREATE OR REPLACE AI FUNCTION extract_clinical_document(pdf_stage_path VARCHAR)
RETURNS VARIANT
LANGUAGE SQL AS
$$
  SELECT AI_COMPLETE(
    'claude-sonnet-4-6',
    PROMPT('You are a clinical document extraction and review model
specializing in risk adjustment coding. Analyze this clinical
document {0} and extract the following fields.

FIELDS TO EXTRACT:
1.  patient_name - Full patient name
2.  date_of_birth - Patient DOB in the format found in the document
3.  medical_record_number - MRN, Hospital ID, SSN, or any patient identifier
4.  provider_name - Doctor/provider name
5.  date_of_service - Procedure date, report date, or encounter date
6.  diagnosis - Primary diagnosis text as stated in the document
7.  comorbidities - Secondary conditions, complications, or co-occurring
    diagnoses (comma-separated if multiple)
8.  medications - Current medications with dosages if available
9.  lab_results - Key lab tests and their status or values
10. diagnosis_specificity - Is the diagnosis documented to the highest
    ICD-10 specificity? Answer: "high" if type, complications, and
    laterality are specified; "medium" if partially; "low" if vague
11. supporting_evidence - Does the clinical note content support the
    stated diagnosis? Answer "yes", "partial", or "no" with explanation
12. documentation_gaps - What clinically relevant information is missing
    that would improve risk adjustment coding accuracy?

For each field return:
- label: the field name exactly as listed above
- value: the extracted text or assessment
- criterion_met: "yes" if clearly present, "no" if not found,
  "insufficient_documentation" if partially present
- rationale: brief explanation
- evidence_quote: verbatim text from the document (must be a findable
  substring in the document)
- page_index: zero-based page number
- confidence: "high", "medium", or "low"

Return ONLY valid JSON, no markdown fences:
{
  "fields": [
    {"label": "...", "value": "...", "criterion_met": "yes",
     "rationale": "...", "evidence_quote": "...",
     "page_index": 0, "confidence": "high"}
  ]
}',
      TO_FILE('@HACK.QUICKAI.PDF_STAGE', pdf_stage_path))
  )
$$;
